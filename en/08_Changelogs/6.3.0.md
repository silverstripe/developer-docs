## Security considerations {#security-considerations}

This release includes several security fixes. Review the vulnerability disclosures for a more detailed description of each security fix. We highly encourage upgrading your project to include the latest security patches.

We have provided severity ratings of the vulnerabilities below based on the CVSS scores. Note that the impact of the vulnerabilities could vary based on the specifics of each project. You can [read the severity rating definitions in the Silverstripe CMS release process](/contributing/release_process/#severity-rating).

### Flush required to protect the assets directory {#assets-htaccess}

The fix for [SS-2026-003](https://www.silverstripe.org/download/security-releases/ss-2026-003) hardens the `.htaccess` file that Silverstripe CMS generates in `public/assets/`, so that Apache denies direct access to PHP and other script files in that directory. An existing project only picks up the new rules once its assets store is flushed. A flush is part of most deployment processes, so for most projects this happens automatically when you deploy. If yours does not flush, run `sake db:build --flush`, `sake flush`, or a request with `?flush=1` yourself after upgrading.

The `.htaccess` file only applies to Apache. If you serve the site with another webserver such as nginx, you need to configure the equivalent protection yourself - see [webserver configuration](/developer_guides/files/file_security/#webserver-configuration) for the rules to apply. We also recommend repeating the denial in your core Apache configuration, as described on the same page, so that it still applies if the generated `.htaccess` file is missing or overridden.

### Dev task URLs ask for confirmation again {#dev-task-confirmation}

In CMS 5, opening the URL of a dev task in a browser, such as `dev/tasks/MyTask`, showed a "Confirm potentially dangerous action" screen before the task ran, unless the site was in `dev` mode. Previously in CMS 6, [`DevelopmentAdminConfirmationMiddleware`](api:SilverStripe\Control\Middleware\DevelopmentAdminConfirmationMiddleware) only asked for confirmation on URLs that exactly matched a registered dev route such as `dev/tasks`, so following a link straight to an individual task ran it immediately.

As part of the fix for [CVE-2026-91115](https://www.silverstripe.org/download/security-releases/cve-2026-91115), the middleware also asks for confirmation for URLs nested under a registered route, as it did in CMS 5.

If you trigger dev tasks by requesting their URLs from a script or scheduled job, those requests now receive the confirmation screen instead of running the task. We recommend running tasks from the command line with `sake` instead.

### `i18nTextCollectorTask` only accepts a `Writer` class name {#i18n-text-collector-writer}

As part of the fix for [CVE-2026-91115](https://www.silverstripe.org/download/security-releases/cve-2026-91115), the `writer` option of [`i18nTextCollectorTask`](api:SilverStripe\Dev\Tasks\i18nTextCollectorTask) now only accepts the name of a class that implements [`Writer`](api:SilverStripe\i18n\Messages\Writer), and throws an `InvalidArgumentException` for any other value, including an injector service name.

### Email fields in `silverstripe/userforms` and `symbiote/silverstripe-advancedworkflow` no longer evaluate template syntax {#form-email-template-injection}

The subject and body of a user defined form email recipient (handled by [`UserDefinedFormController`](api:SilverStripe\UserForms\Control\UserDefinedFormController) in `silverstripe/userforms`), and the email template of a [`NotifyUsersWorkflowAction`](api:Symbiote\AdvancedWorkflow\Actions\NotifyUsersWorkflowAction) in `symbiote/silverstripe-advancedworkflow`, are edited by CMS authors and were previously rendered through the full template engine. Templates are compiled to PHP and can call methods on arbitrary objects, so an author could have put template code in those fields that ran on the server when the email was sent - for example to change another user's password or to write a PHP file.

[CVE-2026-88991](https://www.silverstripe.org/download/security-releases/cve-2026-88991), [SS-2026-001](https://www.silverstripe.org/download/security-releases/ss-2026-001) and [SS-2026-006](https://www.silverstripe.org/download/security-releases/ss-2026-006) in `silverstripe/userforms`, and [CVE-2026-88990](https://www.silverstripe.org/download/security-releases/cve-2026-88990), [SS-2026-002](https://www.silverstripe.org/download/security-releases/ss-2026-002) and [SS-2026-007](https://www.silverstripe.org/download/security-releases/ss-2026-007) in `symbiote/silverstripe-advancedworkflow`, are separate vulnerabilities that each reach code execution because these fields were rendered as templates, and are all fixed by no longer rendering these fields as templates. The fields now substitute a known set of variables and leave everything else as literal text. In `silverstripe/userforms` that is the submitted form values, referenced as `$FieldName` or `{$FieldName}`. In `symbiote/silverstripe-advancedworkflow` it is the notification variables the action already exposes, such as `$Member.FirstName`, `$Context.Title`, `$Assignee.Email`, and `$CommentHistory`, in either bare or braced form. In both modules, values substituted into an HTML email body are escaped as before.

These are not the first vulnerabilities in these fields. [CVE-2026-54721](https://www.silverstripe.org/download/security-releases/cve-2026-54721) and [CVE-2026-54718](https://www.silverstripe.org/download/security-releases/cve-2026-54718), released in June 2026, let an author run PHP through a `<%t %>` translation string in the same fields. Their fix changed the template parser, but left the fields rendered as templates, which is what the new fixes address.

Control structures and casting methods that the template engine used to process here, such as an `<% if %>` or `<% loop %>` block or a modifier like `$FieldName.LimitCharacters`, now appear verbatim in the sent email. If a project put template logic in any of these fields, rewrite it to use only the supported variables. If you need conditional or looping logic in a `silverstripe/userforms` email, put it in a developer-controlled HTML email template, which the recipient can select and which is still rendered as a template - see [send email as plain text](https://userhelp.silverstripe.org/en/6/optional_features/userforms/form-submissions/#send-email-as-plain-text).

If you need your own variables in these fields, register them from an [extension](/developer_guides/extending/extensions/). In `silverstripe/userforms`, add to the merge-field map from an `updateMergeFields()` method - a dotted name such as `SiteConfig.Title` is supported, so previously used tokens can be re-added:

```php
// app/src/Extensions/FormEmailMergeFieldsExtension.php
namespace App\Extensions;

use SilverStripe\Core\Extension;
use SilverStripe\Model\ArrayData;

class FormEmailMergeFieldsExtension extends Extension
{
    protected function updateMergeFields(ArrayData $mergeFields, $recipient, $submittedForm): void
    {
        $mergeFields->setField('MyVariable', 'my value');
    }
}
```

In `symbiote/silverstripe-advancedworkflow`, add to the notification variables from an `updateNotificationVariables()` method. The array starts empty, and its entries are merged over the action's own variables, so a custom variable with the same name as a built-in one replaces it:

```php
// app/src/Extensions/WorkflowNotificationVariablesExtension.php
namespace App\Extensions;

use SilverStripe\Core\Extension;

class WorkflowNotificationVariablesExtension extends Extension
{
    protected function updateNotificationVariables(array &$customVariables, $workflow): void
    {
        $customVariables['$MyVariable'] = 'my value';
    }
}
```

Apply each extension to its controller or action through [configuration](/developer_guides/extending/extensions/):

```yml
# app/_config/email-field-extensions.yml
SilverStripe\UserForms\Control\UserDefinedFormController:
  extensions:
    - App\Extensions\FormEmailMergeFieldsExtension
Symbiote\AdvancedWorkflow\Actions\NotifyUsersWorkflowAction:
  extensions:
    - App\Extensions\WorkflowNotificationVariablesExtension
```

The registered values are substituted as literal text and are never evaluated as a template. In an HTML email body a plain string value is escaped - pass a `DBField` instance if you need to control the casting.

### Action may be required for groups that grant privileged permissions {#group-privileged-permissions}

Previously, [`Group::canEdit()`](api:SilverStripe\Security\Group::canEdit()) looked only for permission codes assigned directly to the group. A user with the `CMS_ACCESS_SecurityAdmin` permission could therefore edit a group whose members receive privileged permissions through an assigned [`PermissionRole`](api:SilverStripe\Security\PermissionRole), or by inheritance from a parent group. The parent group check in [`Group::validate()`](api:SilverStripe\Security\Group::validate()) likewise ignored permissions granted through a role.

As part of the fix for [CVE-2026-91112](https://www.silverstripe.org/download/security-releases/cve-2026-91112), both now resolve the permissions a member of the group would actually receive, whether those are assigned to the group directly, granted through a role, or inherited from an ancestor group. `Group::canEdit()` also now covers `APPLY_ROLES` as well as `ADMIN`, since a user holding `APPLY_ROLES` can assign an existing role that grants `ADMIN`.

A user without the `ADMIN` permission can no longer edit a group that grants `ADMIN` or `APPLY_ROLES` to its members, and can no longer move a group underneath a group granting a [privileged permission](api:SilverStripe\Security\Permission->privileged_permissions). Groups granting `EDIT_PERMISSIONS` remain editable, so a delegated security administrator can still manage them. If your project relies on `CMS_ACCESS_SecurityAdmin` users administering groups that grant `ADMIN` or `APPLY_ROLES`, we recommend granting those users `ADMIN`, or restructuring the groups so they no longer confer those permissions.

### XML and SVG data URIs removed from HTML content {#xml-svg-data-uris}
<!-- markdownlint-enable title-case-style -->

The fixes for [CVE-2026-88987](https://www.silverstripe.org/download/security-releases/cve-2026-88987) and [CVE-2026-88988](https://www.silverstripe.org/download/security-releases/cve-2026-88988) change [`XssSanitiser`](api:SilverStripe\Core\XssSanitiser) so that it removes the `src`, `lowsrc`, `href` and `data` attributes from an element when the attribute value is a data URI with one of these media types, as it already did for `data:text/html`:

- `data:application/xhtml+xml`, `data:text/xml` and `data:application/xml`. An XML document whose root element is in the XHTML namespace is parsed as XHTML by the browser, which executes any inline `<script>` the document contains.
- `data:image/svg+xml`, and any other media type starting with `data:image/svg`. An SVG is a document that can carry script.

This applies to content saved through the WYSIWYG editor, which is sanitised by [`HTMLEditorSanitiser`](api:SilverStripe\Forms\HTMLEditor\HTMLEditorSanitiser). The media type alone determines whether the attribute is removed - the contents of the data URI are not inspected, so a `data:text/xml` URI which contains no script is removed as well. Data URIs for other image types, such as `data:image/png`, are left alone.

This includes `<img src="data:image/svg+xml;base64,...">`. An SVG referenced by an `<img>` element is rendered with scripting disabled, so that case does not execute anything on its own, but it is removed as well because nothing stops the same value being moved into an attribute that does execute it.

HTML is sanitised when it is saved rather than when it is rendered, so upgrading does not rewrite content you have already stored. If existing content contains an inline SVG image, that image is removed the next time an author saves the record it belongs to. We recommend replacing any such image with an uploaded file before that happens. References to `.svg` files in the asset store are not affected by this change. Those are governed by [`File.allowed_extensions`](api:SilverStripe\Assets\File->allowed_extensions), which does not include `svg` by default.

### Protected files are served with a content disposition {#file-content-disposition}

As part of the fix for [CVE-2026-91111](https://www.silverstripe.org/download/security-releases/cve-2026-91111), files that the asset store serves through PHP, such as draft files and `silverstripe/userforms` submission uploads, are now sent with a `Content-Disposition` header. Only content types listed in [`FlysystemAssetStore.inline_content_types`](api:SilverStripe\Assets\Flysystem\FlysystemAssetStore->inline_content_types) are served as `inline`. Everything else is served as `attachment` and downloads rather than rendering in the browser. Content types listed in [`FlysystemAssetStore.forbidden_inline_content_types`](api:SilverStripe\Assets\Flysystem\FlysystemAssetStore->forbidden_inline_content_types) are always served as `attachment`, even when they match an entry in the allowlist.

The defaults are:

```yml
SilverStripe\Assets\Flysystem\FlysystemAssetStore:
  inline_content_types:
    - 'image/*'
    - 'audio/*'
    - 'video/*'
    - 'application/pdf'
    - 'text/plain'
  forbidden_inline_content_types:
    # Matches "image/*" but can carry an inline <script>
    - 'image/svg+xml'
```

The content type is detected from the file's contents, falling back to the file extension when the contents are inconclusive. A CSV file is detected as `text/csv` from its extension, for example, rather than as the `text/plain` its contents resemble, so it downloads. Markup that a browser could execute, such as SVG or HTML, is always detected from the contents, so renaming such a file does not change how it is served.

[`FlysystemAssetStore.file_response_headers`](api:SilverStripe\Assets\Flysystem\FlysystemAssetStore->file_response_headers) now also includes `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`. If you have overridden that configuration property in your own YAML you are replacing the whole array, and we recommend adding both headers to your override.

Projects using the default [`File.allowed_extensions`](api:SilverStripe\Assets\File->allowed_extensions) need do nothing. With those defaults, archive, office document and CSV files change from inline to downloading, which is what browsers already did with them. XML-based files such as KML, which browsers previously displayed as XML, now download as well. If you have added extensions such as `svg`, `html` or `json`, files with those content types now download when opened directly. Files embedded in a page are unaffected, because browsers ignore `Content-Disposition` for images and media loaded as subresources. We recommend adding any content type you need to render inline to `inline_content_types`.

### Markup in `silverstripe/userforms` required field labels is no longer rendered {#userforms-required-label-escaping}

`silverstripe/userforms` appends an identifier to the label of every required field when the [`UserDefinedForm.required_identifier`](api:SilverStripe\UserForms\Model\UserDefinedForm->required_identifier) configuration property is set. Previously, building that label cast the field title to raw HTML, so markup a content author entered as a field title was rendered as HTML on the public form. As part of the fix for [SS-2026-005](https://www.silverstripe.org/download/security-releases/ss-2026-005), the title is now escaped before the identifier is appended.

This only affects sites that set `required_identifier`, which is unset by default. On those sites, a field title containing markup such as `<strong>` or a link previously rendered as HTML and now renders as visible text. Without `required_identifier` the title was already escaped, so the same title now renders the same way whether or not that configuration property is set.

If you relied on markup in a field title, we recommend moving that content into the field's description or elsewhere on the page.

### Creating records through a `GridFieldDetailForm` enforces create permission {#gridfield-create-permission}

As part of the fix for [CVE-2026-88989](https://www.silverstripe.org/download/security-releases/cve-2026-88989), saving a new record through [`GridFieldDetailForm`](api:SilverStripe\Forms\GridField\GridFieldDetailForm) now calls `canCreate()` on that record and returns a 403 response when it fails, matching the check already applied to the "Add" button. Previously the permission was only checked when rendering the button, so a crafted request could reach the save handler directly and create a record the member was not permitted to create.

No action is required for projects whose `canCreate()` implementations already reflect who may create each record. If you have a `GridFieldDetailForm` for a model whose `canCreate()` returns `false` for members who were previously able to add records through it, those members will now receive a 403 response when saving. Update the model's `canCreate()` to grant the permission if that creation should be allowed.

### Action may be required for media embeds {#media-embed-sandboxing}

The fix for [CVE-2026-54720](https://www.silverstripe.org/download/security-releases/cve-2026-54720) now removes all but a known-safe set of attributes, such as `src`, `width`, `height` and `allow`, from an `<iframe>` returned by an oEmbed provider when that iframe is added to the page as-is rather than wrapped in a sandbox. Removed attributes include event handlers, `style` and `class`. If this breaks a legitimate embed, you can exempt a fully trusted provider's domain with the [`EmbedShortcodeProvider.domains_excluded_from_sandboxing`](api:SilverStripe\View\Shortcodes\EmbedShortcodeProvider->domains_excluded_from_sandboxing) configuration property, so its embeds are left exactly as the provider sends them:

```yml
# app/_config/embed.yml
SilverStripe\View\Shortcodes\EmbedShortcodeProvider:
  domains_excluded_from_sandboxing:
    - trusted-provider.com
```

The domain is matched by suffix, so the value above also matches subdomains such as `embed.trusted-provider.com` - and any other domain ending in the same string, including an unrelated `nottrusted-provider.com`. Give the full domain, so you don't match a domain you don't control.

Embeds from an excluded domain render exactly as the provider sends them, and are no longer wrapped in a sandboxed iframe, so only add domains you fully trust. See [sandboxing oembed HTML](/developer_guides/forms/field_types/htmleditorfield/#sandboxing-oembed-html) for more about how sandboxing works.

## Features and enhancements

### Image editing {#image-editing}

Content authors can now make simple composition changes to images without leaving the CMS: crop, rotate in 90 degree steps, flip horizontally or vertically, and resize.

In the "Files" section, click an image to open its detail view, then click the "Other actions" button - the three dots next to "Save" and "Publish" - and select "Edit image". The action only appears for raster images you have permission to edit.

![Image editor](../_images/image-editor.png)

The editor is focused on image composition (where the subject sits in the frame) rather than retouching i.e. there are no brightness, colour, filter, or background removal controls.

Note the following behaviours:

- **The original file is replaced in place.** Applying an edit writes the rendered result over the origin file. The record keeps its ID, folder, and filename, so everything already using that image picks up the edited pixels with nothing to repoint.
- **The original can be backed up first.** A checkbox in the editor - ticked by default - copies the pre-edit bytes into a new draft file in the same folder before the replacement is written, named by the CMS's usual de-duplication, so `beach.jpg` is backed up as `beach-v2.jpg`. Untick it and the original bytes are gone for good.
- **The edit is saved as a draft.** The published version of the file is untouched, so the live site keeps serving the pre-edit image until you publish it yourself.
- **Resizing keeps the aspect ratio.** Type a width or a height and the other is derived. The output can only be made smaller than the cropped image, never larger.
- **Raster images only.** SVG files are not editable through the image editor.

Being able to edit an image requires permission to edit the original - its bytes are modified - and permission to create files in the folder it lives in, for the backup copy.

Edited images are encoded in the same format as their source, at the same quality used for [resampled images](/developer_guides/files/images/#resampled-image-quality), or at a quality you configure for the editor alone.

Extension hooks are called either side of each write the editor makes, so you can alter the rendered image before it is saved - to add a watermark, for example - or react once it has been.

See [image editor](/developer_guides/customising_the_admin_interface/image_editor/) for the rest of the configuration options.

### React class components converted to functional components {#react-functional-components}

Form field components in the CMS have been converted from React class components to functional components. This is part of an ongoing modernisation effort - functional components are simpler, have better tooling support, and align with current React best practices.

For most projects this change is invisible. However, if your project extends any of these components as an ES6 class (`extends TextField`), that pattern will no longer work because functional components cannot be subclassed.

To ease migration, the original class-based implementations are preserved as `Legacy`-prefixed copies in `client/src/legacy/ReactComponents/`. Only class components that were previously defined in the [`client/src/bundles/bundle.js`](https://github.com/silverstripe/silverstripe-admin/blob/3.2/client/src/bundles/bundle.js) file in `silverstripe/admin`, or were a parent class of an exported component, are available as legacy components. If your project subclasses a converted component, update the import to use the legacy version:

Before:

```js
import TextField from 'components/TextField/TextField';

class MyCustomField extends TextField {
  // ...
}
```

After:

```js
import LegacyTextField from 'legacy/ReactComponents/LegacyTextField';

class MyCustomField extends LegacyTextField {
  // ...
}
```

You will need the latest version of [@silverstripe/webpack-config](https://www.npmjs.com/package/@silverstripe/webpack-config) to use the legacy components, which includes an updated externals configuration to support the new import paths.

Note that these legacy class components are provided as a short-term migration aid and will be removed in CMS 7. Projects should plan to move away from class inheritance before then.

The new functional components provide exports (for example `getInputProps()`, `handleChange()`, and `render()`) that were previously provided via class inheritance. If you previously extended class components, migrate to functional components by composing the exported helpers in your own components.

### SingleRecordAdmin permission generation {#singlerecordadmin-permissions}

Previously, [`SingleRecordAdmin`](api:SilverStripe\Admin\SingleRecordAdmin) subclasses did not generate CMS access permissions in the way that [`ModelAdmin`](api:SilverStripe\Admin\ModelAdmin) subclasses did. This meant it was difficult to grant non-admin users access to custom `SingleRecordAdmin` sections through the CMS security permissions interface - they were only visible to users with administrator privileges without adding custom code.

We've now updated the permission generation system in [`LeftAndMain::providePermissions()`](api:SilverStripe\Admin\LeftAndMain::providePermissions()) to include both `ModelAdmin` and `SingleRecordAdmin` subclasses. Any custom `SingleRecordAdmin` implementation will now automatically generate a permission that allows you to control access via groups and roles, just as you would for `ModelAdmin` sections. By default these permissions will be disabled for non-admin users, so you will need to explicitly grant access to the relevant user groups via the CMS.

If you have a custom `SingleRecordAdmin` that should not appear in the permissions interface, set the [`LeftAndMain.skip_permission_generation`](api:SilverStripe\Admin\LeftAndMain->skip_permission_generation) configuration property value to `true`:

```php
namespace App\Admins;

class MySpecialAdmin extends SingleRecordAdmin
{
    private static bool $skip_permission_generation = true;
    // ...
}
```

### `DoormanRunner` service name now gets the default process limit {#doorman-runner-default-rules}

Previously, if you configured `symbiote/silverstripe-queuedjobs` to run jobs with the [`DoormanRunner`](api:Symbiote\QueuedJobs\Tasks\Engines\DoormanRunner) by its `DoormanRunner` service name - `'%$DoormanRunner'`, as [configuring runners](/optional_features/queuedjobs/configuring-runners/#doorman) shows - the runner did not get its default rules, so Doorman ran job processes with no limit. Referencing the runner by its full class name was not affected.

The `DoormanRunner` service name is now a reference to the `Symbiote\QueuedJobs\Tasks\Engines\DoormanRunner` service, so it gets the default rule, which runs one job process at a time. If your project relied on running jobs in parallel, raise the limit on the `DefaultRule` service:

```yml
SilverStripe\Core\Injector\Injector:
  DefaultRule:
    properties:
      # The number of job processes Doorman can run at the same time
      Processes: 4
```

If your project sets properties on the `DoormanRunner` service name, for example `DefaultRules` as the [multi process execution in Doorman](/optional_features/queuedjobs/performance/#multi-doorman) example currently does, move them to the `Symbiote\QueuedJobs\Tasks\Engines\DoormanRunner` service name. Configuration under `DoormanRunner` now replaces the reference, so any use of the queued jobs service fails with "Class DoormanRunner does not exist".

When you move your own `DefaultRules`, key each rule by name and set `DefaultRule` to `null`. A plain list of rules is added to the module's `DefaultRule` instead of replacing it, and that rule still limits Doorman to one process:

```yml
SilverStripe\Core\Injector\Injector:
  Symbiote\QueuedJobs\Tasks\Engines\DoormanRunner:
    properties:
      DefaultRules:
        # Remove the module's default rule, which limits Doorman to one process
        DefaultRule: null
        # Your own rules, keyed by name - each must be a rule service your project defines
        MyLowUsageRule: '%$MyLowUsageRule'
        MyHighUsageRule: '%$MyHighUsageRule'
```

Only set `DefaultRule` to `null` when you add rules of your own. With no rules, Doorman has no process limit.

This fix was also released in `symbiote/silverstripe-queuedjobs` 6.2.3.
