## Security considerations {#security-considerations}

This release includes security fixes that were previously released as patches for earlier release lines. Review the vulnerability disclosures for a more detailed description of each security fix.

We have provided severity ratings of the vulnerabilities below based on the CVSS scores. Note that the impact of the vulnerabilities could vary based on the specifics of each project. You can [read the severity rating definitions in the Silverstripe CMS release process](/contributing/release_process/#severity-rating).

The following fixes were previously released as patches for earlier release lines:

- [SS-2026-008 Unauthenticated remote code execution via form submissions](https://www.silverstripe.org/download/security-releases/ss-2026-008) Severity: Critical
- [SS-2026-009 Login bypass for accounts without a password](https://www.silverstripe.org/download/security-releases/ss-2026-009) Severity: Critical

These fixes were released in November 2026 in patches for every release line from CMS 4.13 to CMS 6.3, including release lines that have reached end of life. See the [Critical Silverstripe CMS security patches November 2026](https://www.silverstripe.org/blog/critical-silverstripe-cms-security-patches-november-2026) blog post for more about these fixes.

### Form handler methods must be allowed actions {#form-action-dispatch}

As part of the fix for [SS-2026-008](https://www.silverstripe.org/download/security-releases/ss-2026-008), [`FormRequestHandler`](api:SilverStripe\Forms\FormRequestHandler) only calls a handler method on the form when that method is an allowed action, which is the check it already applied to handler methods on the controller and on the request handler. A method is allowed when a [`FormAction`](api:SilverStripe\Forms\FormAction) in the form's actions has that name, or when it is listed in the `allowed_actions` configuration of the request handler. A request whose `action_*` field names any other method on the form now returns a 403 response.

Forms that declare a `FormAction` for each handler method are unaffected. If a custom form reaches a handler method on the form through an `action_*` field without a matching `FormAction`, declare the action so the method stays reachable:

```php
$actions = FieldList::create(
    FormAction::create('doMyThing', 'Do my thing')
);
```

If the action has no button (for example, an AJAX call), move the handler onto a `FormRequestHandler` and list it in `allowed_actions`:

```php
// app/src/Forms/MyFormHandler.php
namespace App\Forms;

use SilverStripe\Control\HTTPRequest;
use SilverStripe\Control\HTTPResponse;
use SilverStripe\Forms\Form;
use SilverStripe\Forms\FormRequestHandler;

class MyFormHandler extends FormRequestHandler
{
    private static $allowed_actions = [
        'doSubmit',
    ];

    public function doSubmit(array $data, Form $form, HTTPRequest $request): HTTPResponse
    {
        // ... handle the submission ...
        return $this->redirectBack();
    }
}
```

Then return it from `buildRequestHandler()` on the form:

```php
// app/src/Forms/MyForm.php
namespace App\Forms;

use SilverStripe\Forms\Form;
use SilverStripe\Forms\FormRequestHandler;

class MyForm extends Form
{
    protected function buildRequestHandler(): FormRequestHandler
    {
        return MyFormHandler::create($this);
    }
}
```

`allowed_actions` is not valid on a `Form` subclass itself. Define it on the controller or a `FormRequestHandler` subclass.

### Members without a password can no longer log in with a blank password {#blank-password-login}

As part of the fix for [SS-2026-009](https://www.silverstripe.org/download/security-releases/ss-2026-009), [`MemberAuthenticator::checkPassword()`](api:SilverStripe\Security\MemberAuthenticator\MemberAuthenticator::checkPassword()) rejects a blank password. Previously a member saved without a password could log in through the email and password login form with a blank password by using a specially crafted malicious request, because the stored hash was of the empty string. Such a member now needs a password set, for example through the "lost password" form, before they can log in through that form.

This only affects the email and password login form. Members without a password can still log in through any other authenticator, such as a single sign-on module.

## Features and enhancements

### New module to display user documentation {#userdocs-admin}

We have created a new module ([`silverstripe/userdocs-admin`](https://www.github.com/silverstripe/silverstripe-userdocs-admin)) that adds a new CMS section to display documentation aimed towards users of the CMS.

This module will be installed by default for any new project using [`silverstripe/installer`](https://www.github.com/silverstripe/silverstripe-installer), and existing projects which have [`silverstripe/recipe-cms`](https://www.github.com/silverstripe/recipe-cms) as a dependency. If you want to install this module in an existing project that doesn't use that recipe, you will need to install it to that project yourself.

By default this module will automatically include documentation for the [commercially supported modules](/project_governance/supported_modules/). You can also add documentation for your own modules and project-specific functionality, as well as override and localise documentation. See [Userdocs admin developer docs](/optional_features/userdocs-admin/) for details.

### HTML5 `<meta charset>` {#html5-meta-charset}

Pages now declare their character encoding with the HTML5 `<meta charset="utf-8">` instead of `<meta http-equiv="Content-Type" content="text/html; charset=utf-8">`, which the W3C validator flags.

- [`SiteTree::MetaComponents()`](api:SilverStripe\CMS\Model\SiteTree::MetaComponents()) now returns the `contentType` entry with a single `charset` attribute instead of the `http-equiv` and `content` attributes, and lists it first, so `$MetaTags` renders it as the first tag. The array key stays `contentType`.
- The `BlankPage.ss` templates in `silverstripe/framework` and `silverstripe/cms`, and the `LeftAndMain.ss`, `CMSDialog.ss` and `LeftAndMain_printable.ss` templates in `silverstripe/admin`, use `<meta charset="utf-8">`. `LeftAndMain_printable.ss` now uses the HTML5 doctype instead of XHTML 1.1, and takes its `lang` attribute from the current CMS locale.

The HTTP `Content-Type` response header is unchanged.

If you read or modify `$tags['contentType']['attributes']['content']` or `$tags['contentType']['attributes']['http-equiv']` in an `updateMetaComponents()` extension or a `MetaComponents()` override, use `$tags['contentType']['attributes']['charset']` instead. If your templates add their own charset meta tag next to `$MetaTags`, remove it so the page doesn't declare the encoding twice. See [modifying meta tags](/developer_guides/templates/common_variables/#modifying-meta-tags).

### Limit on lost password requests {#lost-password-limit}

[`LostPasswordHandler`](api:SilverStripe\Security\MemberAuthenticator\LostPasswordHandler) now limits how many password reset emails it sends for a member from one IP address.

By default, once an IP address has requested 3 reset emails for a member, it is locked out for 15 minutes. During the lockout, requests show the usual confirmation page but no email is sent. You can change the limit with [`LostPasswordHandler.lock_out_after_reset_requests`](api:SilverStripe\Security\MemberAuthenticator\LostPasswordHandler->lock_out_after_reset_requests) and [`LostPasswordHandler.lock_out_delay_mins`](api:SilverStripe\Security\MemberAuthenticator\LostPasswordHandler->lock_out_delay_mins), or set `lock_out_after_reset_requests` to `0` to disable it:

```yml
SilverStripe\Security\MemberAuthenticator\LostPasswordHandler:
  lock_out_after_reset_requests: 3
  lock_out_delay_mins: 15
```

### Other new features and enhancements {#other-new}

- [`InterventionBackend::getImageResource()`](api:SilverStripe\Assets\InterventionBackend::getImageResource()) no longer creates a temporary file before handing assets to Intervention Image. Instead it leverages functionality from Intervention Image 3 that reads EXIF data directly from the stream.

## API changes

### Deprecated API

The following API has been deprecated in this release, and will be removed or replaced in a future major release.

It's best practice to avoid using deprecated code where possible, but sometimes it's unavoidable. This API will all continue to be available at least until the next major release.

- The [`Director::is_cli()`](api:SilverStripe\Control\Director::is_cli()) method has been deprecated. Use [`Environment::isCli()`](api:SilverStripe\Core\Environment::isCli()) instead.
- The [`InterventionBackend::getTempPath()`](api:SilverStripe\Assets\InterventionBackend::getTempPath()) method has been deprecated and will be removed without a replacement.
- The [`InterventionBackend::setTempPath()`](api:SilverStripe\Assets\InterventionBackend::setTempPath()) method has been deprecated and will be removed without a replacement.
- The [`InterventionBackend.local_temp_path`](api:SilverStripe\Assets\InterventionBackend->local_temp_path) configuration property has been deprecated and will be removed without a replacement.

## Bug fixes

This release includes a number of bug fixes to improve a broad range of areas. Check the change logs for full details of these fixes split by module. Thank you to the community members that helped contribute these fixes as part of the release!

### External link URLs longer than 255 characters {#linkfield-long-external-urls}

Previously, the `ExternalUrl` field on [`ExternalLink`](api:SilverStripe\LinkField\Models\ExternalLink) in [silverstripe/linkfield](/optional_features/linkfield/) was a `Varchar` column, which holds at most 255 characters. Saving a longer URL cut it off at 255 characters, so the link pointed somewhere else. The field is now a `Text` column.
