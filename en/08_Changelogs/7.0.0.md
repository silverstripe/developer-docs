## Features and enhancements

### Publish permission checks on owned records {#owned-publish-permissions}

Previously, CMS publish actions only checked `canPublish()` on the record being published. An author who could not publish a file directly could still put someone else's unpublished file changes live by linking the file in a page and publishing the page.

CMS publish actions now call [`canPublishRecursive()`](api:SilverStripe\Versioned\RecursivePublishable::canPublishRecursive()), which also checks every owned record with unpublished changes. Owned records are checked with `canPublish()`, the same check that applies when publishing them directly.

Authors can no longer publish a record that would put unpublished changes to an owned record live, such as a file or an element, unless they can publish that owned record. Shared assets with pending changes, for example a logo, block publishing of the records that own them until someone with the right permission publishes the asset.

New installs give the default "Content Authors" group the `FILE_EDIT_ALL` permission. Existing sites keep their current group permissions, so this is an upgrade step. Before you upgrade, grant `FILE_EDIT_ALL` or folder edit permissions to each group whose members publish pages that use files. Without it, those authors cannot publish a page that would put changed files live. This includes a file that they just uploaded, because a file that was never published counts as changed.

When a publish is blocked, the error message now names the owned records that blocked it. A blocked publish from the CMS page editor or a GridField still saves the draft, and the message says so. A batch publish counts a blocked page as a failure instead of skipping it.

[`publishRecursive()`](api:SilverStripe\Versioned\RecursivePublishable::publishRecursive()) and [`ChangeSet::publish()`](api:SilverStripe\Versioned\ChangeSet::publish()) are unchanged and still do not check permissions, so tasks, queued jobs and workflow actions that publish without a logged in member are not affected. If you have a custom controller that calls `publishRecursive()` for a member, we recommend calling `canPublishRecursive()` first, and again after saving any form data that could add owned records. To show the reason to the author, call [`validatePublishRecursive()`](api:SilverStripe\Versioned\RecursivePublishable::validatePublishRecursive()), which returns a `ValidationResult` with the error message. See [versioning](/developer_guides/model/versioning/#ownership) for details.

## API changes

### Grant file permissions before upgrading {#owned-publish-upgrade}

Existing sites must grant file permissions to the groups whose members publish pages that use files, or those authors are blocked from publishing. See [publish permission checks on owned records](#owned-publish-permissions) for the upgrade step.
